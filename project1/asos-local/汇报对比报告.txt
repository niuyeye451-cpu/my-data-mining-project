九、关键结论
---------------------------------------------------------------------------------

  1. 老师代码在 2026 年 ASOS 页面上全部失效。
     根本原因：ASOS 从静态 HTML 面板架构重构为 SPA + JSON 注入架构。
     - 列表页不再使用 <article id="product-xxx">
     - 详情页不再使用 <button> 展开面板
     - 属性名从 class/id 变为 data-testid/JSON key

  2. 我的代码通过多层适配成功运行：
     - 列表页：滚动触发懒加载 + 通用 XPath 兜底
     - 详情页：解析 window.asos.pdp.config JSON 直接读取字段
     - 数据校验：validate_data() 6 维度防止错误页入库

  3. 融合了老师的长处：
     - 多线程思路（task2.py 已实现可配并发）
     - urlretrieve 简洁思路（task4.py 继承了精简 API 风格）
     - 字段完整性（向老师的 14 字段看齐并全部打通）

  4. 创新点：
     - JSON config 直接提取（比 DOM 面板点击更稳健）
     - 页面 URL 跳转检测（识别 ASOS 错误重定向）
     - 错误页模式匹配（10 种文本模式，防止假成功）
     - 断点续爬队列（status=0→1→2 状态机）

十一、时效性分析：我的代码会像老师的一样失效吗？
---------------------------------------------------------------------------------

  核心原则：没有任何爬虫代码是永久有效的，网站随时可能改版。但防失效能力有强弱之分。

  11.1 失效风险评估（逐个字段）

  ┌──────────────────┬─────────────────────┬──────────┬──────────────────────┐
  │ 提取方法          │ 依赖项               │ 失效风险 │ 分析                  │
  ├──────────────────┼─────────────────────┼──────────┼──────────────────────┤
  │ //h1             │ HTML 语义标签        │ 🟢 极低   │ 标题必用 h1，是 HTML  │
  │                  │                     │          │ 标准，几乎不可能改动   │
  ├──────────────────┼─────────────────────┼──────────┼──────────────────────┤
  │ /prd/ 正则        │ URL 路由规范         │ 🟢 极低   │ SEO 友好 URL 是电商    │
  │                  │                     │          │ 基础设施，改造成本极高  │
  ├──────────────────┼─────────────────────┼──────────┼──────────────────────┤
  │ //select          │ HTML 语义标签        │ 🟢 极低   │ 尺码选择器必用 <select>│
  ├──────────────────┼─────────────────────┼──────────┼──────────────────────┤
  │ window.asos.pdp.  │ JS 数据注入          │ 🟡 中    │ JSON key 可能改名，但  │
  │ config            │                     │          │ 数据注入模式不会消失   │
  ├──────────────────┼─────────────────────┼──────────┼──────────────────────┤
  │ gallery-image     │ 特定 CSS class      │ 🔴 高    │ 最容易改，纯前端 class  │
  ├──────────────────┼─────────────────────┼──────────┼──────────────────────┤
  │ images.asos-media │ CDN 域名            │ 🟡 中    │ CDN 迁移会导致失效，   │
  │ .com              │                     │          │ 但不频繁               │
  └──────────────────┴─────────────────────┴──────────┴──────────────────────┘

  11.2 多层防御设计（与老师代码的本质区别）

  老师代码的失效模式：
      单一依赖 → 一个点失效，全部崩溃
      例：class='ojIeyOc' 没了 → 面包屑失效 → 整个爬虫因为没 try/except 直接崩溃

  我的代码的失效模式：
      多层兜底 → 一个点失效，自动降级
      例：JSON config 改了 key → 正则从 page_source 提取 → 仍失败则返回空字符串不崩溃

  ┌────────────────────────────────────────────────────────────────┐
  │  每个字段的提取策略都是：                                         │
  │                                                                  │
  │  第一层（最优）→ 失败 → 第二层（兜底）→ 失败 → 返回空值           │
  │                                                                  │
  │  品牌：JSON-LD → 正则 brandName → title 首词                     │
  │  价格：current-price span → data-testid 备选 → 空字符串          │
  │  描述：ID=productDescription → XPath 备选 → 空字符串             │
  │  材质：pdp.config.aboutMe → page_source 正则 → 空字符串          │
  │  洗护：pdp.config.careInfo → page_source 正则 → 空字符串         │
  │                                                                  │
  │  validate_data() 作为最后一层防线：                               │
  │  → 即使所有提取都"成功"，如果数据不对（错误页、跳转、空价格）     │
  │  → 标记为 status=2，不会产生脏数据                               │
  └────────────────────────────────────────────────────────────────┘

  11.3 老师失效 vs 我的失效 — 对比

  ┌────────────────────────────────┬────────────────────────────────┐
  │ 老师代码（2024 → 2026）         │ 我的代码（面对未来 ASOS 改版）   │
  ├────────────────────────────────┼────────────────────────────────┤
  │ 硬编码 DOM 层级路径            │ 语义化选择器（JSON key/标签名）  │
  │ class='ojIeyOc'               │                                   │
  │ #looksVariantSelector         │ //select (HTML 标准)             │
  │ #productDescription/ul/li[5]  │ JSON 键名（比 DOM 路径稳定）      │
  │                                │                                   │
  │ 无 try/except                  │ 每个提取点都有 try/except        │
  │ 异常 = 程序崩溃                │ 异常 = 字段空值 + status=2       │
  │                                │                                   │
  │ 无可观测性                     │ validate_data() 失败时打印原因   │
  │ 不知道哪里坏了                 │ 知道哪个字段/哪种模式失效         │
  │                                │                                   │
  │ 一次性代码                     │ 渐进式降级，修改成本低            │
  │ 改版 = 全部重写                │ 改版 = 只需更新个别提取方法        │
  └────────────────────────────────┴────────────────────────────────┘

  11.4 最坏情况推演

  假设 ASOS 彻底大改版（更换前端框架、改 CDN、改路由）：

  如果 JSON config 改名 → 需更新正则中的 key 名（5 分钟）
  如果 CDN 换域名 → 需更新 images_dir 中的域名过滤（从 images.asos-media.com 改为新域名，3 分钟）
  如果 /prd/ URL 格式变了 → 需更新正则（10 分钟）
  如果 h1 不存在 → 几乎不可能，这是 SEO 刚需

  结论：
      最坏情况下需要修改约 5-10 行代码（更新 JSON key 名或 XPath），
      而不是像老师代码一样从头重写。
      这是"可维护的时效性" vs "一次性代码"的本质区别。

  11.5 直言结论

  会失效吗？                  会，任何爬虫最终都会因目标网站改版而需要维护。
  会像老师代码一样 100% 崩溃吗？ 不会。多层兜底保证了渐进降级，不是瞬间全灭。
  维护成本有多高？            低。几行 key/XPath 更新，不用重写架构。
  什么时候需要关注？          当 validate_data() 大面积报失败时，说明 ASOS 已改版，
                             需要检查 JSON config key 名或 XPath 是否需要更新。
